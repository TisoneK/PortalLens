## Executive Summary

`PortalReport.open_questions` was `list[str]` — prose at the bottom of a report. That made "what would resolve this?" a sentence a human had to write consistently, and left a graph view unable to lay a gap out. It is now `list[OpenQuestion]`: `subject`, `question`, an optional relationship `kind` (the edge that would be established if answered), and `resolves_with` (analysis-step slugs that could answer it). This is the first slice of ADR-9 — model + migration; the `AnalysisStep` registry that owns the slugs and computes a "next investigation" queue is a later slice.

Migrated all four consumers: the analyzer (emits structured questions), the Markdown renderer (prints `Resolves with:`), the TUI panel (shows a `next:` hint), and the tests. The investigation store (ADR-8) needed **no change** — `OpenQuestion` is pydantic, so it serialized into the existing JSON round-trip for free, exactly as the ADR-8 review predicted.

Test suite: 135 → **138** passing. Ruff + mypy strict clean. Verified end-to-end, including that the structured questions survive the SQLite persist/reload across separate processes.

## What was built

### `OpenQuestion` (`portal.py`)

```python
class OpenQuestion(BaseModel):
    subject: str                       # the entity the gap is about
    question: str                      # the prose prompt
    kind: RelationshipKind | None = None   # the edge drawn if answered
    resolves_with: list[str] = []      # analysis-step slugs that could answer it
```

Design decisions worth recording:

- **`kind` is the graph seam.** Set only when a question maps to a *specific missing edge* — the upstream-ISP question carries `UPSTREAM_OF`, so a future graph view draws it as an explicit unknown edge rather than burying it in prose. Questions that refine an existing node (e.g. "who's the legal entity behind this operator host?") leave `kind=None`.
- **Empty `resolves_with` is meaningful, not lazy.** A documented-only signature's "does this hold in the field?" question names no step, because no automated technique validates a signature — it needs a real captured URL. The empty list *is* that statement, and a test asserts it (distinguishing it from the upstream/admin questions, which do name steps).
- **Slugs are plain strings for now.** `resolve_dns`, `ip_asn_lookup`, `probe_tls`, `port_scan`, `capture_html` — module constants in the analyzer. The `AnalysisStep` registry that will own them (and compute a runnable "next investigation" queue) is the next slice; keeping slugs as strings kept this slice small and self-contained.

### Migration

- `analyzer._open_questions()` now returns `list[OpenQuestion]`, building each with subject/kind/resolves_with. Prose is byte-for-byte the same as before, so the human-readable output is unchanged — only the structure around it is new.
- `reporting/` renders `- {question}` plus a `  - Resolves with: …` sub-line.
- `tui/widgets.py::OpenQuestionsPanel` renders the question plus a `next: …` hint; I added `rich.markup.escape` on the question and slug text (the session-4 TUI lesson: raw report text into `Text.from_markup` can be mis-parsed as markup).

## Findings

No defects found or introduced. One observation:

### N-1 — `resolves_with` slugs are not yet validated against a registry
The slugs are free strings; nothing checks that `"ip_asn_lookup"` corresponds to a real step, because the registry doesn't exist yet. This is intended (the registry is the next slice), but until it lands a typo in a slug would be silent. When the `AnalysisStep` registry arrives, add a test that every `resolves_with` slug the analyzer emits is a registered step.
