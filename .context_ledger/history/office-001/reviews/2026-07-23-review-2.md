## Executive Summary

The MVP shipped in session 1 works, but it only works for ISPMan. The provider
was not a parameter of the analysis — it was spread through the source as an
enum member, two module constants, a hand-written detector function, and six
string comparisons against `"ispman.tech"`. Adding a second provider would
have meant editing four files, and the relationship reasoning ("who operates
this network?", "is this operator a reseller?") would have had to be
duplicated per vendor.

Provider knowledge now lives in one registry (`signatures.py`) as data. The
parser, the fingerprint scorer, and the relationship analyzer iterate that
registry and name no vendor. Two further providers and one further gateway
were added purely as registry entries, and a test registers a fourth at
runtime to prove the extension point is real.

**Every confidence score on the existing ISPMan fixture is byte-identical**,
verified by rendering the report from the pre-refactor commit in a separate
worktree and diffing. That diff also surfaced a defect: `USES_PLATFORM` and
`AUTHENTICATES_FOR` were each emitted twice.

Test suite: 55 → 80 passing. Ruff and mypy strict clean throughout.

## What was built

### `signatures.py` — the registry

A `PortalSignature` record carries everything PortalLens knows about one
platform: the rules that decide whether it fires, the weight each matched
signal contributes, the display name, and the rule's provenance.

`SignatureRule` expresses a firing condition declaratively — required
parameters, any-of parameters, a minimum count of the platform's known
variables, host suffixes, path prefixes/suffixes. A signature fires if any of
its rules matches. All four pre-existing detection behaviours were expressible
without a custom predicate, which is why the confidence scores came out
unchanged.

### The gateway / hosted-platform split

The first implementation conflated two different layers under one "flavor"
enum. The registry separates them:

- **Gateway** — software on the operator's own hardware that emits the
  redirect (MikroTik, CoovaChilli, UniFi). Identified by its query variables,
  which travel with the redirect. Owns no hostname.
- **Hosted platform** — a third party running the portal on the operator's
  behalf (ISPMan, Meraki). Identified by its own host + path scheme.

This split is what makes the relationship reasoning provider-agnostic. A
redirect landing on *any* hosted-platform host supports `USES_PLATFORM` and
`AUTHENTICATES_FOR`; a host owned by a hosted platform is never reported as
the network operator. Neither rule names a vendor.

### Provenance

The project's core claim is calibration, so a rule transcribed from vendor
documentation must not read like one checked against a real captured URL.
Every signature records which it is. `MIKROTIK` and `ISPMAN` are `VALIDATED`
(the `tests/data` fixture is a real capture). `COOVACHILLI`, `UNIFI`, and
`MERAKI` are `DOCUMENTED` — when one of them fires, the fingerprint note says
so and the report adds an open question inviting the reader to discount it.

**This is a deliberate honesty mechanism and should not be quietly dropped.**
The alternative — shipping documentation-derived signatures that present
identically to field-validated ones — would undermine the confidence model.

### `flavors` became a list of slugs

`CaptivePortalURLHints.flavors` now holds plain slug strings rather than
enum members, so a registry entry needs no enum member. `CaptivePortalFlavor`
survives as a convenience enum over the built-in slugs; because it derives
from `str`, existing `CaptivePortalFlavor.MIKROTIK in hints.flavors` checks
keep working unchanged.

## Findings

### H-1 — Duplicate relationships in every hosted-platform report (High)

- **Description:** `infer_relationships` built its ISPMan redirect list from
  two sources — redirects whose *target* was ISPMan, and (when the primary URL
  was itself ISPMan) redirects whose target was the primary host. On the real
  fixture both matched the same pair, so `USES_PLATFORM` and
  `AUTHENTICATES_FOR` were each emitted twice, in the relationships table, the
  inferences list, and the executive summary's count ("Inferred
  relationships: 6" where 4 was correct).
- **Impact:** A reader counting corroborating relationships would double-count.
  In a disclosure report, that reads as more evidence than exists — the exact
  failure mode the confidence model is designed to prevent.
- **Why session 1 missed it:** the CLI output was read for correctness of each
  line, not for duplicates across lines.
- **Fix:** `_platform_redirects()` dedupes on `(source, platform.slug)`.
  Regression test `TestNoDuplicateRelationships::test_each_relationship_appears_once`.
- **Status:** fixed — `de8c6bd`

### M-1 — Fingerprint host weight applied without checking the host (Medium)

- **Description:** `_detect_ispman` added its 60-point host weight for *any*
  `URL_HOST` evidence on the primary URL. It was only reachable when the
  ISPMan flavor had already fired, so it was not exploitable — but the weight
  was not conditioned on the thing it claimed to measure.
- **Impact:** Latent. Any future code path reaching the scorer without the
  flavor pre-check would have scored an arbitrary host at 60.
- **Fix:** `_weight_for()` applies `host_weight` only when
  `signature.owns_host(ev.value)`.
- **Status:** fixed — `de8c6bd`

### M-2 — Host suffix matching had no label boundary (Medium)

- **Description:** the original check was
  `host == "ispman.tech" or host.endswith(".ispman.tech")`, which is correct.
  Generalizing it to arbitrary registry entries made it easy to get wrong, so
  the boundary rule is now enforced in one function (`host_matches`) with a
  test: `evilispman.tech` does not match `ispman.tech`.
- **Impact:** Prevented rather than fixed — an attacker registering a
  lookalike domain would otherwise be reported as the platform provider.
- **Status:** hardened + tested — `de8c6bd`

### L-1 — Observed-fact statement listed parameters that weren't present (Low)

- **Description:** the MikroTik fact statement was a hardcoded string naming
  `link-login / link-orig / dst / mac / ip` regardless of which of those the
  URL actually carried. On the real fixture, `dst` is absent — the report
  asserted evidence it did not have.
- **Fix:** the statement now names the weighted parameters actually observed.
- **Status:** fixed — `de8c6bd`

### L-2 — Hosted-platform fact statement restated session identifiers (Low)

- **Description:** the generalized statement initially interpolated the full
  path, copying the operator/hotspot/session UUIDs into a sentence meant to be
  quotable in a disclosure email. The evidence table already carries them.
- **Fix:** the statement names the scheme; the evidence table carries the values.
- **Status:** fixed — `de8c6bd`

### N-1 — `same_host()` is unused (Nice to have)

`url_parser.same_host()` has no caller in `src/` or `tests/`. Left in place —
it is a reasonable public helper for a library — but noted so a future session
doesn't assume it's load-bearing.

## Tests added (25 new, 55 → 80)

`tests/test_signatures.py`:

- **Registry invariants** — unique slugs; hosted platforms declare a hostname;
  gateways declare none; no signature treats an "original destination"
  parameter (`link-orig`, `userurl`) as a redirect (the session-1 false
  positive, now structurally prevented); every signature carries a note and a
  provenance.
- **Host matching** — exact, subdomain, lookalike rejection, unrelated host,
  empty host.
- **Overreach guards** — UniFi requires its controller path, not just a bare
  `id` parameter; Meraki requires `/splash/`, not just its hostname.
- **A second provider end to end** — a Meraki-hosted MikroTik gateway yields
  the Meraki fingerprint, the provisional-signature note, `USES_PLATFORM` and
  `AUTHENTICATES_FOR` naming Meraki, and does not report the Meraki host as
  the network operator.
- **A provider that exists nowhere in the source** — registered at runtime and
  picked up by the parser, the scorer (80% = host 60 ⊕ path 50, the same
  noisy-OR any other platform gets), and the relationship analyzer.
- **Duplicate-relationship regression** (H-1).
