# PortalLens Review — 2026-07-23 (Session 4)

> Session 4 review. Target: ADR-7 — the investigation-console TUI (accepted as a design decision in session 3, not yet implemented). This session implements it. Produced under the `.context/` AI Engineering Protocol, cloud/sandbox edition.

## Executive Summary

ADR-7 is now implemented. The investigation-console TUI is a pure presentation layer over the engine: it receives a fully-analyzed `PortalReport` and renders it, never running analysis itself. It is built with Textual, shipped behind the optional `portallens[tui]` extra, and is responsive from ~40 columns (Termux, portrait) to wide desktop. Severity and status are never colour-only — every confidence badge carries its label text alongside its percentage. No vendor hostname is baked into any screen.

The CLI is now a `click.Group` with `analyze` + `tui` subcommands. A custom `_DefaultAnalyzeGroup` falls back to `analyze` when the first positional arg isn't a known subcommand, so `portallens <urls>` still works — the pre-TUI invocation form that session-1 / session-2 scripts may depend on is preserved.

Quality gates: **102/102 tests passing** (22 new), ruff clean, mypy strict clean. Verified headlessly on a 40-column terminal — the relationship view reports `narrow=True` and the app renders without error.

### High

### Medium

**M-1: First-pass `Static.render()` returned `str`, not `Text` — Textual 8.x rejects it.**
- **Description:** The first widget draft had `render(self) -> str` returning a markup string. Textual 8.x's `Static.render()` returns a `Text`/`Strip`, not a bare `str`. The TUI tests failed with `AttributeError: 'str' object has no attribute 'get_height'` when Textual tried to measure the rendered content.
- **Impact:** Every panel failed to render — the TUI was non-functional until fixed.
- **Recommendation (implemented):** Introduced a `_ReportText` base class whose `render()` returns `rich.text.Text` built via `Text.from_markup(...)`. Subclasses implement `_build_text() -> Text`. All panels now render correctly.
- **Status:** Fixed in commit `e06107a`.

**M-2: First-pass `confidence_markup` produced nested markup that Textual parsed as a style tag.**
- **Description:** `confidence_markup(88)` returned `[bold green][very_high · 88%][/bold green]`. Textual's `Text.from_markup` parsed the inner `[very_high · 88%]` as a style tag and failed with `MissingStyle: Failed to get style 'very_high · 88%'`.
- **Impact:** Every confidence badge failed to render — same non-functional TUI as M-1.
- **Recommendation (implemented):** Escape the literal brackets around the badge: `[bold green]\[very_high · 88%][/bold green]`. `Text.from_markup` unescapes `\[` to a literal `[` on render, so the badge displays as `[very_high · 88%]` with the `bold green` style applied to the whole badge.
- **Status:** Fixed in commit `e06107a`.

### Low

**L-1: First-pass no-vendor-literals test scanned docstrings and comments.**
- **Description:** The first `test_no_vendor_literals_in_tui_source` read the raw `.py` file text and grepped for `maz.wifi` / `captive.ispman.tech`. It failed immediately because the TUI module docstrings legitimately reference those names as examples ("`maz.wifi` and `captive.ispman.tech` never appear as literals...").
- **Impact:** False-positive test failure; the test was too strict for its own purpose.
- **Recommendation (implemented):** Rewrote the test to walk the AST and scan only `ast.Constant` string nodes (executable string literals), not docstrings or comments. Docstrings that reference vendor names as examples are fine; a screen hardcoding a vendor name as a default/placeholder is the actual violation.
- **Status:** Fixed in commit `e06107a`.

**L-2: `git checkout -- .` reverted real edits along with mode-only changes.**
- **Description:** Mid-session, I ran `git config core.fileMode false && git checkout -- .` to discard spurious file-mode changes (100644→100755) the sandbox filesystem had applied to every tracked file. The `checkout -- .` reverted the mode changes AND my real edits to `cli.py`, `pyproject.toml`, `README.md`, `CHANGELOG.md`, `docs/ARCHITECTURE.md`, and `tasks/current.md`. Only untracked new files (`tui/`, `test_tui.py`) survived.
- **Impact:** ~15 min redoing the tracked-file edits. No data lost (the new TUI package was intact; the edits were mechanical to re-apply).
- **Recommendation:** When the sandbox flips file modes, use `git config core.fileMode false` alone — that's enough to make `git status` ignore mode changes. Do NOT follow it with `git checkout -- .`; that discards working-tree changes indiscriminately. Logged in `inefficiencies/log.md`.
- **Status:** Worked around by re-applying the edits. No code change needed.

### Nice to Have

**N-1: `_DefaultAnalyzeGroup.resolve_command` line is 121 chars.**
- **Description:** The `resolve_command` signature with its full return-type annotation is 121 characters, over the 100-char `line-length` in `pyproject.toml`.
- **Impact:** None functionally — ruff's `E501` is ignored (line length is enforced by the formatter, not the linter), and ruff passes.
- **Recommendation:** Could be split across lines for readability, but the signature reads more clearly on one line. Leave as-is unless a future formatter enforces it.
- **Status:** Not fixed — deliberate.
