# PortalLens Review — 2026-07-23

> Session 1 review report. Covers the bootstrap of `.context/` (core 0.2.0) and the MVP feature implementation: `Portal` core abstraction + `captive_wifi` passive analyzer + Markdown reporting + CLI. Produced under the `.context/` AI Engineering Protocol, cloud/sandbox edition.

## Executive Summary

The session bootstrapped `.context/` on the previously-empty PortalLens repository and implemented the full MVP described in the PortalLens design conversation. The implementation is evidence-backed from end to end: every inference cites the evidence it rests on, every hypothesis is capped at `low` confidence by convention, and the analyzer is **passive by default** — active techniques (HTTP fetching, DNS resolution, port scanning) are gated behind an explicit `AcquisitionPolicy` and a CLI `--i-have-authorization` flag.

The MVP was validated end-to-end against the actual ISPMan URL pair the user pasted in the design conversation (`maz.wifi` → `captive.ispman.tech`). The analyzer correctly identifies both platforms (ISPMan 80% / MikroTik 78%), infers the redirect (75%), the platform relationship (80%), the authentication relationship (75%), the network operator (74%), and explicitly flags the "reseller vs. operator-using-platform" question as a 35% hypothesis — exactly the calibrated, evidence-backed output the design called for.

## Findings

### Critical

### High

### Medium

**M-1: `link-orig` parameter was initially treated as a portal-redirect signal.**
- **Description:** The first version of `relationship.py` inferred `REDIRECTS_TO` relationships from both `link-login` AND `link-orig` parameters. `link-orig` is the URL the user was originally trying to reach (e.g. Apple's captive probe `http://www.msftconnecttest.com/redirect`), not a portal-to-portal redirect. Treating it as one produced a false-positive "msftconnecttest.com redirects to captive.ispman.tech" inference in the first CLI run.
- **Impact:** False-positive relationships in the report; reader confusion.
- **Recommendation (implemented):** Only `link-login` and `link-login-only` are used for redirect inference. `link-orig` is captured as evidence but not used for relationship inference. Documented in `relationship.py` docstring.
- **Status:** Fixed in commit `84fea3b`.

**M-2: Fingerprints were initially only detected on the primary URL.**
- **Description:** The first version of `analyzer.py` called `detect_fingerprints(primary_hints, evidence)` only. When the primary URL was `maz.wifi` (which only carries `dst` — the MikroTik entry signature), the analyzer missed the ISPMan fingerprint that lived on the other URL (`captive.ispman.tech`).
- **Impact:** Incomplete platform detection when the user supplies both the local captive hostname and the external portal URL.
- **Recommendation (implemented):** The analyzer now runs `detect_fingerprints` for every supplied URL, dedupes by `(platform, version)`, and keeps the highest-confidence match. Documented inline.
- **Status:** Fixed in commit `84fea3b`.

### Low

**L-1: MikroTik detection was initially too strict.**
- **Description:** The first version of `url_parser.py` required either `{link-login, link-orig}` together OR ≥4 keys from the MikroTik set. The `maz.wifi/login?dst=...` entry URL only has `dst` — neither condition fired, so the local captive hostname wasn't recognized as MikroTik at all.
- **Impact:** The local captive hostname (`maz.wifi`) was classified as `GENERIC` rather than `MIKROTIK`, and the relationship inference couldn't use it as a redirect source.
- **Recommendation (implemented):** Relaxed detection to also fire on `dst` alone when the path starts with `/login` (the canonical MikroTik hotspot login entry point). The fingerprint detector weights `dst` low on its own, so this still produces a low-confidence fingerprint for the entry URL — honest about the thin evidence.
- **Status:** Fixed in commit `84fea3b`.

**L-2: Initial CLI had a convoluted monkey-patch for the `--i-have-authorization` flag.**
- **Description:** The first CLI draft used a wrapper function + module-level `_confirmed_authorization` helper that was monkey-patched at call time. Worked, but unreadable.
- **Impact:** Maintainability risk; future contributors would struggle to add new gated flags.
- **Recommendation (implemented):** Rewrote as a single `@click.command` with `--i-have-authorization` as a normal `is_flag` option, checked directly in the function body.
- **Status:** Fixed in commit `84fea3b`.

### Nice to Have

**N-1: `score()` noisy-OR combination could be exposed as a public API.**
- **Description:** `portallens.confidence.score` is the canonical way to combine evidence weights, but it's not in `__all__` for the top-level package. Subclasses use `Portal.confidence(value)` for single-evidence inferences, but multi-evidence combination requires importing `score` directly.
- **Recommendation:** Either add `score` to `portallens.__all__` (already done in `__init__.py`) OR document the convention that subclasses should use `score([w1, w2, ...])` for multi-evidence inferences. The latter is already documented in `portal.py`'s `Portal` docstring.
- **Status:** Resolved — `score` is exported in `portallens.__all__`.

## Fixes Applied

All fixes are in commit `84fea3b` (the MVP feature commit):

1. **M-1:** `relationship.py` — restricted redirect inference to `link-login` and `link-login-only` parameters only. `link-orig` is captured as evidence but not used for redirect inference.
2. **M-2:** `analyzer.py` — fingerprints now detected across ALL supplied URLs, deduped by `(platform, version)`, highest-confidence match kept.
3. **L-1:** `url_parser.py` — relaxed MikroTik detection to fire on `dst` + `/login` path (the canonical entry signature). Fingerprint detector weights `dst` low on its own.
4. **L-2:** `cli.py` — rewrote as a single `@click.command` with `--i-have-authorization` as a normal flag.

4. **HTML fingerprinting** — the `EvidenceType` enum already includes `HTML_ELEMENT` and `JS_BUNDLE`, but the analyzer doesn't yet capture HTML evidence. Add an opt-in `--html-file URL:PATH` CLI flag (stub exists) and an HTML fingerprint detector.
5. **DNS resolution** — `AcquisitionPolicy.resolve_dns` is defined but no code uses it. Add a `portallens/acquisition/dns.py` module that resolves a hostname and emits `EvidenceType.DNS_RECORD` evidence.
6. **IP/ASN lookup** — required to close the "who is the upstream ISP?" open question. Not started; needs a free IP/ASN API (e.g. RIPEstat) integration behind `AcquisitionPolicy`.
7. **SARIF output** — for security-audit findings, SARIF is the industry standard. Add `render_sarif()` alongside `render_markdown()` in `reporting/`.
