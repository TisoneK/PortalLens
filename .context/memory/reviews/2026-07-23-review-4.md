## What was built

### `portallens/investigation/` — a new package

- **`models.py`** — `Investigation` (pydantic), `AuthorizationGrant`, `AuditEntry`.
  - `Investigation.start(report, portal_type=...)` is the factory: stamps timezone-aware UTC timestamps and opens the audit log with a `created` entry. Timestamps are **always UTC, never naive** — an audit trail in an unstated local zone is worse than useless read from another.
  - `authorize(technique, note=...)` validates the technique, appends a grant **and** an audit entry, bumps `updated_at`. Re-authorizing appends a second grant rather than collapsing — each assertion is separately-timestamped evidence.
  - The id is derived from the **actual target host** (`captive.ispman.tech` → `captive-ispman-tech-<6hex>`). That's data, not a hardcoded example; the hex suffix keeps revisits distinct.
  - `ACTIVE_TECHNIQUES` is **derived from `AcquisitionPolicy`'s boolean fields**, not hardcoded — so ADR-13's future `use_osint_apis` / `execute_scripts` flags become authorizable with no edit here. A test pins the current five so the derivation can't silently drift.

- **`store.py`** — `InvestigationStore` (SQLite).
  - **Document-in-SQLite:** queryable facts (id, target, portal_type, created/updated) are promoted to indexed columns; the full aggregate is a JSON `data` column. Deliberate — the report shape is still evolving (ADR-9 steps), so a brittle relational schema now costs more than it buys. The columns serve DisclosureDesk's future queries; the JSON gives the aggregate room. When a column is needed, a migration promotes it.
  - **Migration ledger:** schema version in `PRAGMA user_version`; `_MIGRATIONS` is an ordered list applied on connect. Fresh and old databases converge by running every migration past their version. Next schema change is an append, never a rewrite (ADR-8's "migrations from day one"). Re-opening a migrated DB is idempotent — tested.
  - `save` is an upsert; `get` / `list` / `delete` / `count`; context-manager; `list` reads only columns (no JSON deserialized).
  - Path resolution: `--db` → `$PORTALLENS_DB` → `$XDG_DATA_HOME/portallens/investigations.db` → `~/.local/share/...`. `:memory:` supported.

### CLI — four subcommands (`cli.py`)

`investigate` (analyze + save, prints id), `investigations` (list newest-first), `show <id>` (render stored report, or `--audit` for the trail), `authorize <id> --technique <t>` (record a timestamped grant). All share the existing `_run_analysis()` helper and the `--db` option. The session-4 `_DefaultAnalyzeGroup` fallback still routes bare `portallens <urls>` to `analyze`; the four new names are known subcommands so they aren't hijacked.

## Findings

No defects found or introduced. Observations:

### N-1 — `list()` summary carries no counts (Nice to have)
`InvestigationSummary` has id/target/type/dates but not finding/fingerprint counts, because counts would require deserializing the JSON per row (defeating the point of promoted columns). If a listing wants "3 findings" per row, promote a count column in a migration rather than loading every payload. Noted, not done — premature now.

### N-2 — no `delete` CLI subcommand
The store supports `delete()` but no CLI verb exposes it. Deliberate: deleting an investigation is destructive and the disclosure trail is the whole point, so I did not add a one-keystroke destroy. If wanted later, gate it behind a confirmation prompt.

### N-3 — concurrent writers
SQLite's default locking handles the "two processes, occasional writes" case fine, but there's no explicit busy-timeout set. If PortalLens ever grows a long-running writer (a TUI holding the store open while a CLI writes), add `PRAGMA busy_timeout`. Not a concern at current usage.
